# Argo CD and Argo Rollouts: Git Reconciliation, Field Ownership and Recovery

Argo CD and Argo Rollouts solve different problems in the release path. This guide shows how to use them together for safer canary and blue-green delivery on Kubernetes.

## TL;DR

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-1)

Argo CD and Argo Rollouts manage different parts of a release. Argo CD reconciles reviewed manifests from Git, while Rollouts manages candidate replicas, promotion steps and configured traffic changes. Verify the observed Git revision, candidate template, analysis outcomes and real request destination separately. Declare ownership of controller-managed fields and keep drift exclusions narrow. During recovery, distinguish Rollouts abort from a Git revert and from Argo CD application rollback, which is unavailable with automated sync enabled. Rehearse success and failure paths in staging. These documentation-based examples do not claim a DevOpsDreams deployment or tested recovery duration.

## Define the integration task before changing Git

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-2)

This guide covers how a reviewed Git change reaches an Argo Rollout and how operators reconcile desired state after an abort. Choose the canary or blue-green strategy, traffic router and measurement policy first using the [strategy and analysis guide](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-with-canary-and_01578260684.html). The integration task is to establish ownership and observable checkpoints across Git, Argo CD, Rollouts and the router.

## Argo CD and Argo Rollouts Are Not the Same Tool

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-3)

Argo CD and Argo Rollouts sit at different layers.

Argo CD owns reconciliation. It watches the Application definition in Git, renders the desired manifests, and makes the cluster match that desired state. The Application spec gives you the source, destination, and sync policy, including automated sync, prune, self-heal, and retry refresh behavior.

Argo Rollouts owns release strategy. It replaces the plain Deployment release mechanism with a Rollout resource that can move through canary or blue-green phases, run analysis, and use supported traffic routers when you need weighted exposure.

That split keeps the model clean:

- Git defines what should exist.
- Argo CD makes sure it exists.
- Argo Rollouts decides how the new version should be exposed.

The Kubernetes Deployment controller is the baseline comparison, not the target design. Deployments are strong for rolling updates and readiness-gated replacement, but they do not give you a first-class control plane for staged traffic shifts, analysis-driven promotion, or rollback policy tied to metrics. That is the line progressive delivery crosses.

### A practical control-plane split

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-a-practical-control-plane-split)

The important design question is not "Can we run Argo CD and Argo Rollouts together?" They are designed to work together. The important question is which layer owns which behavior.

- Argo CD owns desired-state reconciliation.
- Argo Rollouts owns release strategy and version exposure.
- Kubernetes Deployment remains the baseline if you do not need a higher-order rollout controller.

If you blur those boundaries, the system becomes hard to debug. If Argo CD is expected to manage traffic weights, or if Argo Rollouts is expected to author Git, you have already lost the clean model.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: checkout
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example-org/platform-gitops.git
    targetRevision: main
    path: apps/checkout
  destination:
    server: https://kubernetes.default.svc
    namespace: checkout
  syncPolicy:
    automated:
      enabled: true
      prune: true
      selfHeal: true
    retry:
      refresh: true
```

  

Argo Rollouts adds staged promotion and analysis on top of GitOps reconciliation.

## Reconcile the intended canary revision

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-4)

Argo CD applies the reviewed Rollout specification; Rollouts advances the selected steps and owns its generated ReplicaSets and configured routing updates. Inspect the Application commit and the candidate pod template together. An Application reporting Synced does not establish that the candidate passed analysis or that requests reached it. For complete strategy examples, use the [strategy guide](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-with-canary-and_01578260684.html).

## Separate Git synchronization from traffic promotion

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-5)

For blue-green, synchronizing a manifest and promoting the candidate are separate decisions. With manual promotion, verify the preview revision, required AnalysisRuns, active/preview Service selection and readiness before authorizing the switch. scaleDownDelaySeconds retains the previous ReplicaSet after promotion; abortScaleDownDelaySeconds affects the new preview after abort. dynamicStableScale belongs to traffic-routed canary, not blue-green. These fields require controller/router validation.

## Treat analysis status as release evidence

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-6)

AnalysisTemplate inputs must match the exporter labels and isolate the intended revision. Check the resulting AnalysisRun and measurements rather than equating Git synchronization with release success. Failed, inconclusive and erroneous measurement outcomes need deliberate operator responses. Missing telemetry or inadequate traffic cannot demonstrate safety. Keep thresholds and queries in the [strategy guide](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-with-canary-and_01578260684.html) and verify the instrumentation contract in staging.

## Rollout Lifecycle

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-7)

The lifecycle is what turns the separate tools into one operational system.

1. A developer changes the manifest in Git.
2. Argo CD sees the Application as OutOfSync and applies the new desired state.
3. The Rollout controller creates or updates the active ReplicaSet.
4. The traffic router shifts exposure according to the canary or blue-green plan.
5. Analysis runs against the live version and produces a pass, fail, or inconclusive result.
6. The rollout either promotes the new version or aborts back to the stable version.

That sequence is why the roles matter. Argo CD is not the traffic shifter. Argo Rollouts is not the Git system. The traffic router is not the policy engine. Each layer has one job.

## Declare ownership of controller-managed fields

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-8)

Declare which fields Git owns and which the rollout/router controller modifies, such as generated Service selector hashes or traffic weights. Inspect actual differences before adding narrowly scoped ignore rules. Argo CD ignoreDifferences controls comparison; applying that policy during synchronization requires the relevant sync behavior, including RespectIgnoreDifferences when appropriate. Broadly ignoring every Service or route can conceal unrelated drift. Verify the chosen controller and Argo CD release. [Diff customization](https://argo-cd.readthedocs.io/en/stable/user-guide/diffing/); [sync options](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-options/#respect-ignore-differences-configs).

## Choosing The Traffic Router

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-9)

Traffic management is the part most teams underestimate. Argo Rollouts supports traffic-aware delivery, but the support is not generic. It is provider-specific, and the manifest shape depends on the router you actually run.

That means the right question is not "Does Argo Rollouts support traffic?" The right question is "Does my router support the release pattern I need, and does it do so in the way I expect?"

In practice, verify all of the following before standardizing on a router integration:

- Whether the provider supports weighted traffic for canary releases.
- Whether the provider supports a preview path for blue-green promotion.
- Whether the traffic shift is request-level, route-level, or service-selector-based.
- How long it takes for selector or routing changes to propagate.
- Whether aborting a rollout returns traffic to the stable version immediately or after a delay.

That last point matters because some integrations rely on service selector propagation, which is not instantaneous. The release controller can request a change, but the cluster data plane still has to honor it. That is why fields like `scaleDownDelaySeconds` exist and why you should treat them as safety controls rather than optional decoration.

If you do not have traffic routing at all, canary still has value, but only as a best-effort exposure model. In that mode, replica weighting is not the same as exact request weighting, and you should not present it to operators as if it were.

For critical services, prefer a router configuration that you can test end to end in staging with the same ingress or service-mesh behavior you expect in production. The gap between "supported in docs" and "works under load" is where most rollout surprises live.

## What To Validate In Staging

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-10)

Before you let a rollout strategy touch production, validate the whole release loop in an environment that looks enough like production to expose the failures you care about.

- Confirm Argo CD applies the correct manifest revision and respects sync ordering.
- Confirm the Rollout controller moves through the intended canary or blue-green phases.
- Confirm the traffic router actually shifts exposure the way the manifest says it should.
- Confirm analysis can succeed, fail, and remain inconclusive without leaving the rollout in a confusing state.
- Confirm abort behavior returns service to the stable revision in the time window you expect.
- Confirm the rollback story is still acceptable when automated sync is enabled.
- Confirm your alerting can tell the difference between a blocked rollout and a broken rollout.

This is the point where good teams learn whether the strategy is safe enough for their traffic profile. A staged rollout only helps if the failure path is just as deliberate as the happy path.

## Safety Caveats

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-11)

Progressive delivery still has sharp edges, and the docs are explicit about them.

- `scaleDownDelaySeconds` matters because traffic propagation is not instantaneous.
- `dynamicStableScale` changes how much capacity the stable ReplicaSet keeps during rollout.
- `abortScaleDownDelaySeconds` affects how quickly the old version disappears after an abort.
- Weighted canary without a traffic router is only a best-effort model based on replica placement, not exact request-level split.
- Argo CD automated sync does not make rollback trivial; the Argo CD docs note that rollback cannot be performed against an application with automated sync enabled.

If you treat those as footnotes, you will eventually get surprised in production.

## What Argo Rollouts Does Not Do

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-12)

Argo Rollouts is easy to misunderstand because it sits near GitOps and traffic management.

- It does not read or write Git.
- It does not replace Argo CD.
- It does not collect metrics itself.
- It does not guarantee zero-downtime releases.
- It does not magically make every traffic provider behave the same way.

The FAQ is clear on the Git boundary: Argo Rollouts changes the cluster state for the release, but it has no Git repository knowledge of its own. Argo CD owns the Git link.

## A Practical Operating Model

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-13)

If you are introducing progressive delivery to a real cluster, start with a narrow policy:

1. Keep the Application in Argo CD automated sync mode.
2. Use Rollouts for only the services that justify the extra control plane.
3. Start with canary if you need gradual exposure, or blue-green if you need a clean cutover path.
4. Add analysis gates before you trust the rollout to auto-promote.
5. Expand router-specific traffic management only after the basic control loop is stable.

That approach avoids the two common failure modes: over-engineering every service and under-engineering the risky ones.

If you also use Argo CD sync waves, keep them for dependency ordering and bootstrap sequencing, not for traffic promotion. Sync waves solve apply order. Rollouts solve release exposure.

## Rehearse commit, abort and desired-state recovery in staging

[Section link](https://devopsdreams.blogspot.com/2026/03/progressive-delivery-on-kubernetes-with_0549401167.html#dd-section-14-2)

This is a reference rehearsal, not a tested DevOpsDreams deployment. Choose a disposable staging Application and record a known-good commit and image revision. Submit a reviewed candidate commit, then verify the Application's observed revision, the Rollout's candidate template, Service selectors, router state and AnalysisRun outcomes. Use your own names and namespaces; the following inspection assumes the examples named checkout and checkout-release.

```bash
# Read-only checks; use the real Application and workload namespace.
kubectl -n argocd get application checkout-release
kubectl -n argocd get application checkout-release -o jsonpath='{.status.sync.revision}{"\n"}'
kubectl argo rollouts get rollout checkout -n default
kubectl get analysisruns -n default
kubectl get services checkout-stable checkout-canary -n default
```

For the failure-path rehearsal, deliberately fail a bounded staging analysis or authorize an abort. Verify actual request routing, healthy stable capacity and the resulting Rollout state. Then review a Git revert or corrective manifest commit so desired state matches the chosen recovery. Automated sync can reconcile away ad hoc changes. Argo CD application rollback is unavailable while automated sync is enabled; Rollouts abort and Git revert solve different parts of recovery.

```bash
# Mutation: choose this only as the authorized staging incident action.
kubectl argo rollouts abort checkout -n default
# Read the resulting state; this alone does not prove traffic recovery.
kubectl argo rollouts get rollout checkout -n default
# In the manifest repository, inspect the reviewed recovery change before committing.
git diff
```

Record candidate commit, observed Application revision, candidate and stable pod hashes, analysis outcome, actual request destination and post-recovery Git revision. A complete rehearsal includes a failure or inconclusive path, router propagation and data compatibility. No universal recovery duration is promised. [Automated sync semantics](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/).
